从 v3 的「按一次热键翻一句话」扩到「盯着看也行、专有名词不打架、日语也能认」。

## 二、几个关键设计

### 1. 「要不要翻译这一行」按文字种类判断

最早的规则是「含中文就跳过」（避免把整合包里已经汉化的物品名再翻一遍），后来发现两类误伤：

- OCR 把系统提示和英文台词接到一行 → 半截英文永远翻不出来；
- 日语假名一个英文字母都没有 → 整行被跳过，日语完全翻不了。

现在是：

```
假名 / 谚文 / 西里尔 / 阿拉伯 / 泰文  → 不是目标语言就翻
汉字行                              → 目标不是中文就翻；中英混排（字母够多）也翻；
                                      只有汉字且目标是中文时跳过，
                                      但同一批里出现过假名就当日语处理
纯数字符号 / 字母太少                 → 跳过
```

### 2. 自动术语表只活一天

人名地名最容易前后不一致。模型在返回 JSON 里顺带给出本批的专有名词（`terms` 字段），
应用攒成 `%APPDATA%\mchanhua\terms.json`，下一批请求自动带上。

- 只收「原文里确实出现过」的词（模型编的、整句、和原文一样的都丢掉，一批最多 20 条）；
- 同一个名字后来出现别的译法也**保持第一次的写法**（一致性优先）；
- 默认 24 小时没用到的自动清掉，文件空了直接删（`[terms] ttl_hours` 可改）；
- 用户自己配置的 `[glossary]` 优先级更高，手动修正写进去后就固定了。

### 3. 提示词改版怎么不丢缓存

缓存主键是 `模型 + 提示词版本 + 原文`。改提示词版本会让所有缓存行失效——
包括用户手动修正过的译文。所以启动时会把旧版本的行**改挂到新版本**上
（`TranslationCache.retag_all`），缓存和人工成果都保住。

### 4. Windows OCR 与 rapidocr 不能随便换顺序

在部分机器上**先初始化 winrt（系统 OCR）、再 import rapidocr/onnxruntime 会原生崩溃**
（access violation，python.exe 直接报"内存不能为 read"）。所以：

- 日语/韩语/俄语这条路径先试 rapidocr（有随包模型就用它），再退回系统 OCR；
- `rapidocr_is_unsafe()` 兜底：顺序不对时抛出明确错误，而不是让进程崩掉。

## 三、日语是怎么支持的

1. 判断层：日语行现在能被送去翻译（见上）；
2. 识别层：随包一份 PP-OCRv4 的日语识别模型 + 字典（约 9MB），设置里选「日语」即可；
   检测仍用中英检测模型——实测多语言检测模型会把一行切碎甚至丢掉开头几个字；
3. 拼接层：检测切出来的左右碎片会被接回整句（`merge_lines` 的同行拼接）。

实测（游戏字号，1.3 倍缩放）：

```
ウィンドウサイズの初期化に失敗しました。  → 窗口大小初始化失败了。
もう一度ゲームを起動してください。        → 请重新启动一次游戏。
セーブデータは壊れていません。            → 存档数据没有损坏。
```

## 四、界面动效的取舍

参考了 GitHub 上 `CamusFSY/memphis-python-gui-skill` 的做法（按钮按下要有反馈、
图标要用真实位图而不是 emoji、阻塞工作要有独立进度区），但做了两处调整：

- 该 skill 用"按下时向前景挪 3–5px"做反馈；我们的按钮在等宽网格里，位移会带着整行重排，
  所以改成颜色插值（按下加深、松开回弹）；
- 主窗口尺寸不做动画：它有一套"按内容自适应"的排版逻辑，动画会和它打架。

动画一律是**有限步数**的 `after` 回调（不自我递归），转圈则挂在 60ms 的 poll 上走帧。
